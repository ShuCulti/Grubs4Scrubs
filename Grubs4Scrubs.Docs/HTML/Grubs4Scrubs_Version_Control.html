The Grubs4Scrubs project lives in a GitHub repository. I use Git for version control on both the frontend (React + Vite) and backend (ASP.NET Core). This document explains my workflow: how I commit, how I branch, and what the repo structure looks like.

Commit Practices

I try to commit after completing a logical chunk of work, not after every line change. A commit should represent one thing: "added Recipe View page", "removed Tailwind from Dashboard", "moved models to Domain project". Not "various changes" or "stuff".

What's in .gitignore

Standard ignores for both React and .NET: - node_modules/ (frontend dependencies, reinstalled with npm install) - bin/ and obj/ (.NET build output) - .vs/ (Visual Studio settings) - appsettings.Development.json (local config that might contain connection strings)

Lessons Learned About Version Control

The layered architecture migration taught me the most about Git. I moved files between projects, renamed namespaces, and updated references all in one go. That made for a messy diff. If I did it again, I'd commit after each step: first move the models, commit. Then create the DataAccess project, commit. Then move the repositories, commit. Smaller commits make it way easier to find where something broke if the build fails.

The Tailwind removal was similar. I should've committed after converting each page instead of converting everything and committing once. When something broke, I had to search through a huge diff to find the issue.
